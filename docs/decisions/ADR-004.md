# ADR-004: Authoritative Confirmation Policy Enforcement and Cryptographic Tool Parameter Binding

**Status:** Accepted  
**Date:** 2026-09-12  
**Decision Maker:** Solution Architect / Technical Lead  
**Consulted:** Security Lead, Backend Engineer, Mobile Engineer, QA Lead  

---

## 1. Context & Problem Statement

During the Phase 2 Architecture Security Review (`docs/security/SECURITY_REVIEW_PHASE_2.md`), two critical (`P0`) authorization vulnerabilities were identified:

1. **Confirmation Suppression (`SEC-P0-01`):** In `docs/architecture/PERMISSION_MATRIX.md`, the Policy Engine evaluation algorithm relied on the boolean flag `action.requiresConfirmation` emitted by the untrusted Intent Classifier (`POST /v1/assistant/interpret`) and forwarded by the client. An adversary, malicious prompt injection payload, or compromised client could set `requiresConfirmation: false` on sensitive actions (e.g., `CAP_CALENDAR_WRITE`, `CAP_CONTACT_CALL`), causing the Policy Engine to bypass user confirmation and issue an immediate `executionGrantToken` (`ALLOWED`).
2. **Tool Parameter Substitution & Tampering (`SEC-P0-02`):** In `docs/architecture/API_CONTRACTS.md`, `POST /v1/tools/execute` accepts execution parameters in the request payload independently of the `executionGrantToken`. If the tool executor verifies only the token's cryptographic signature and expiration timestamp without asserting an exact match against the parameters, an attacker could acquire an authorization token for an innocuous action and submit altered parameters (e.g., substituting an attacker-controlled telephone number or contact identifier).

---

## 2. Considered Alternatives

### Alternative A: Rely on Client-Side Confirmation Flags and Token Signatures
- Retain `action.requiresConfirmation` from the intent payload and rely on tool executors verifying token validity alone.
- *Rejection Rationale:* Violates the core non-negotiable security invariant ("AI proposes, Policy authorizes, Tool executes"). An untrusted layer (generative AI or mobile client) cannot be trusted to dictate whether an action requires confirmation, and unbound parameters allow authorization replay with arbitrary payloads.

### Alternative B: Direct UI / Screen Inspection Confirmation
- Require the user to visually inspect on-screen cards or modals.
- *Rejection Rationale:* Sighted-centric design. Sanad's primary demographic is blind and visually impaired Palestinian users who navigate solely via TalkBack screen readers, earcons, and conversational audio.

### Alternative C: Server-Side Authoritative Confirmation Matrix and Parameter Hash Binding (Selected)
- **Authoritative Confirmation Matrix:** The Policy Engine enforces an immutable, server-side lookup table `CAPABILITY_CONFIRMATION_RULES` mapping every capability to `'ALWAYS'`, `'CONDITIONAL'`, or `'NEVER'`. The engine completely ignores any client- or AI-provided `requiresConfirmation` claim.
- **Cryptographic Parameter Hash Binding:** When the Policy Engine grants an execution token, it computes $\text{actionHash} = \text{SHA-256}(\text{targetCapability} + \text{canonical}(\text{slots}))$. Every Tool Executor enforces a strict assertion verifying that the SHA-256 hash of the canonicalized runtime execution parameters exactly equals `token.actionHash`. Any parameter mismatch throws a fatal `TamperedParametersError` and halts execution.

---

## 3. Decision Outcome

We choose **Alternative C**.

### Architectural Standards & Invariants:

1. **Immutable Server-Side Confirmation Matrix:**
   ```typescript
   export const CAPABILITY_CONFIRMATION_RULES: Record<CapabilityId, 'ALWAYS' | 'CONDITIONAL' | 'NEVER'> = {
     CAP_ASSISTANT_QUERY: 'NEVER',
     CAP_ALIAS_MANAGE: 'ALWAYS',
     CAP_SETTINGS_ACCESSIBILITY: 'NEVER',
     CAP_AUDIT_INSPECT: 'NEVER',
     CAP_ACTION_CANCEL: 'NEVER',
     CAP_CONTACT_CALL: 'ALWAYS',
     CAP_MESSAGE_SEND: 'ALWAYS',
     CAP_LOCATION_READ: 'ALWAYS',
     CAP_LOCATION_SHARE: 'ALWAYS',
     CAP_CALENDAR_READ: 'NEVER',
     CAP_CALENDAR_WRITE: 'ALWAYS',
     CAP_EMERGENCY_TRIGGER: 'ALWAYS',
   };
   ```
   No sensitive capability (`HIGH`, `CRITICAL`, or write-enabled) may proceed without an explicit, spoken, audio-confirmed user response.

2. **Deterministic Canonical Parameter Hashing:**
   The parameter hash is defined strictly across backend and mobile runtimes as:
   $$\text{actionHash} = \text{SHA-256}\left(\text{targetCapability} \,\|\, \text{JSON.stringify}(\text{canonicalize}(\text{parameters}))\right)$$
   Where `canonicalize()` recursively sorts object keys lexicographically and enforces uniform UTF-8 string encoding.

3. **Mandatory Executor Hash Assertion:**
   Tool executors must execute parameter hash verification as a core sandbox invariant:
   ```typescript
   const computedHash = computeActionHash(targetCapability, parameters);
   if (computedHash !== authGrant.actionHash) {
     throw new TamperedParametersError(
       `Execution parameters do not match signed authorization grant: expected ${authGrant.actionHash}, got ${computedHash}`
     );
   }
   ```

---

## 4. Consequences

### Positive Consequences
- **Complete Elimination of Confirmation Suppression:** Adversaries cannot bypass spoken confirmations through prompt injection or parameter manipulation.
- **Parameter Integrity:** Single-use execution grants cannot be repurposed to execute unintended real-world side effects.
- **Auditable Security:** Any parameter tampering attempt immediately produces a tamper-evident audit record with incident ID.

### Negative Consequences / Trade-offs
- **Strict Parameter Parity:** Callers cannot introduce undeclared or transient fields into tool parameters without invalidating the token hash.
- **Slight Overhead:** Canonical JSON serialization and SHA-256 hashing adds $< 0.5\text{ ms}$ compute overhead to the policy and execution cycle (well within the $\le 10\text{ ms}$ policy evaluation budget).
