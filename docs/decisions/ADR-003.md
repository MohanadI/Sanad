# ADR-003: Android-First React Native Client with Native Accessibility (TalkBack) Integration

**Status:** Accepted  
**Date:** 2026-09-12  
**Decision Maker:** Solution Architect / Technical Lead  
**Consulted:** Mobile Engineer, QA/Accessibility Engineer, Product Lead  

---

## 1. Context & Problem Statement

Sanad's primary user interface is a mobile application. Blind and visually impaired users rely fundamentally on platform screen readers (Android TalkBack, iOS VoiceOver) and hardware-level audio subsystems to navigate their devices.

In Palestine:
1. **Operating System Demographics:** Over $85\text{–}90\%$ of the target demographic uses Android smartphones, predominantly mid-to-low tier devices (Samsung Galaxy A-series, Xiaomi Redmi, etc.).
2. **Platform Restrictions:** Android allows programmatic intent dispatching, native accessibility service bindings, and granular audio routing that iOS strictly prohibits or tightly restricts.
3. **Resource Constraint:** The mobile engineering capacity for the MVP consists of a single full-time React Native engineer. Attempting simultaneous dual-platform development (Android + iOS) would split testing focus and jeopardize pilot delivery.

---

## 2. Considered Alternatives

### Alternative A: Progressive Web App (PWA)
- Deliver the assistant as an accessible web application via mobile browser.
- *Rejection Rationale:* Web browsers cannot reliably integrate with background audio services, native dialers, address books, hardware volume buttons, or low-level accessibility node trees. Audio latency in mobile browsers is unacceptably high for real-time conversational cues.

### Alternative B: Pure Native Android Application (Kotlin)
- Build exclusively in native Kotlin/Jetpack Compose.
- *Rejection Rationale:* While providing maximum native control, a pure Kotlin codebase eliminates code sharing with the TypeScript backend (DTOs, validation schemas) and would require a complete rewrite from scratch when expanding to iOS in Phase 5.

### Alternative C: Simultaneous Cross-Platform React Native (Android + iOS)
- Build and support both platforms concurrently from Day 1.
- *Rejection Rationale:* Doubling the testing matrix for accessibility (testing both TalkBack and VoiceOver simultaneously) with a 1-person mobile team will cause delivery delays. Furthermore, iOS device ownership among the low-income pilot demographic in Palestine is negligible.

### Alternative D: Android-First React Native with Native Accessibility Bridges (Selected)
- Build the mobile application using React Native, targeting Android exclusively for the MVP pilot.
- Implement custom native Android Kotlin modules for hardware-level audio cues (earcons), low-latency audio capture, and TalkBack live region management.
- Share TypeScript DTOs and schema definitions directly with the backend.
- Defer iOS implementation to Phase 5 (Expansion).

---

## 3. Decision Outcome

We choose **Alternative D: Android-First React Native**.

### Architectural Standards:
1. **Target OS & Version:** Android 8.0+ (API Level 26+), optimized for Android 11–14.
2. **Screen Reader Integration:** Every interactive element explicitly declares `accessibilityRole`, `accessibilityLabel` (in localized Arabic), and `accessibilityLiveRegion`.
3. **Native Modules (Kotlin):**
   - `AudioCueModule`: Pre-caches audio earcons in memory using Android `SoundPool` for sub-$20\text{ ms}$ playback latency.
   - `KeyStoreVaultModule`: Interfaces with Android KeyStore and `EncryptedSharedPreferences` for secure credential storage.
4. **Offline Capability:** Core TalkBack navigation and cached alias dictionaries remain functional during network dropouts.
5. **Phase 5 Roadmapping:** React Native codebase maintains platform-agnostic UI abstractions to allow seamless iOS VoiceOver adaptation once Android pilot validation is complete.

---

## 4. Consequences

### Positive Consequences
- **Target Audience Alignment:** Directly serves the $85\%+$ of Palestinian blind users who own Android devices.
- **Sub-50ms Audio Feedback:** Native `SoundPool` bridge ensures instant earcon feedback, crucial for blind user orientation.
- **Shared Type Safety:** Frontend and backend share identical TypeScript interfaces and Zod validation schemas.
- **Focused Engineering:** Single mobile engineer concentrates entirely on Android TalkBack accessibility edge cases rather than debugging cross-platform discrepancies.

### Negative Consequences / Trade-offs
- **iOS Exclusion:** Palestinian blind users who own iPhones cannot participate in the initial pilot (deferred to Phase 5).
- **Android Fragmentation:** Testing must cover diverse Android OEM skins (Samsung One UI, Xiaomi MIUI) and varying Android TalkBack implementations.
