# ADR-005: Autonomous Native Android Emergency Architecture & Offline Life-Safety Protocol

**Status:** Accepted  
**Date:** 2026-09-12  
**Decision Maker:** Solution Architect / Technical Lead  
**Consulted:** Security Lead, Mobile Engineer, QA/Accessibility Lead, Product Lead  

---

## 1. Context & Problem Statement

During the Phase 2 Architecture Security Review (`docs/security/SECURITY_REVIEW_PHASE_2.md`), a critical boundary vulnerability (`SEC-P1-01`) was identified in the emergency workflow architecture:

- In `docs/architecture/SYSTEM_ARCHITECTURE.md`, `CAP_EMERGENCY_TRIGGER` was modeled as part of the unified cloud pipeline: speech audio transmitted to the backend modular monolith via TLS/WebSocket $\rightarrow$ intent parsed by `POST /v1/assistant/interpret` $\rightarrow$ policy evaluated by `POST /v1/policy/evaluate` $\rightarrow$ mobile tool execution.
- In Palestine, blind and visually impaired users face unique environmental and infrastructural realities: checkpoint signal jammers, rural 2G/3G connectivity loss, network throttling, and frequent mobile data outages.
- If a blind user in acute distress utters *"طوارئ"* (Emergency) while network connectivity is degraded or severed, a cloud-dependent pipeline hangs on network timeouts (10–30 seconds) and fails to dial. This is an unacceptable life-safety failure.

---

## 2. Considered Alternatives

### Alternative A: Cloud-First Architecture with Client Fallback Timeout
- Attempt remote API interpretation first; if network request times out after 5 seconds, fallback to local emergency routine.
- *Rejection Rationale:* Adds unacceptable latency (5+ seconds delay) to an acute emergency situation. A distressed blind user cannot wait for network timeouts before an emergency call initiates.

### Alternative B: Pure SMS Alert Dispatch
- Dispatch an automated background SMS to emergency contacts.
- *Rejection Rationale:* Google Play Store policies severely restrict background SMS (`SEND_SMS`) permissions. Furthermore, SMS does not establish an immediate two-way voice communication channel necessary for life-safety interventions.

### Alternative C: Autonomous Native Android Emergency Subsystem (Selected)
- Decouple `CAP_EMERGENCY_TRIGGER` completely from the cloud backend.
- Implement an autonomous, 100% on-device Android native Kotlin module (`EmergencyNativeModule`).
- Support activation via physical hardware button patterns (e.g. 5 rapid power-button presses) and on-device offline keyword recognition.
- Execute a deterministic 5-second countdown with distinctive audible earcons and speech cancellation ("إلغاء"), culminating in a native telephony dialer intent (`Intent.ACTION_CALL` or `Intent.ACTION_DIAL`).
- Telemetry is stored in an encrypted offline queue and synced to the audit log only when network connectivity is restored.

---

## 3. Decision Outcome

We choose **Alternative C**.

### Architectural Standards & Invariants:

1. **Zero Cloud Dependency for Emergency Execution:**
   The emergency initiation pathway must execute with zero network calls, zero DNS lookups, and zero cloud API roundtrips.
2. **Deterministic On-Device State Machine:**
   ```text
   [Trigger: Hardware Button / Offline Keyword]
         │
         ▼
   [Haptic Pulse + EARCON_EMERGENCY_COUNTDOWN]
         │
         ▼ (5-second window: Spoken "إلغاء" or Volume Rocker aborts)
   [Direct Native Intent: Intent.ACTION_CALL to Trusted Number]
         │
         ▼
   [Local Encrypted Audit Queue (Async Sync when Online)]
   ```
3. **Execution Target Reclassification:**
   In `CAPABILITY_MATRIX.md`, the Execution Target for `CAP_EMERGENCY_TRIGGER` is updated from `Device Native` (server-orchestrated) to `DEVICE_LOCAL_AUTONOMOUS`.
4. **Offline Resilience Testing Requirement:**
   Every release build must pass automated tests simulating complete network loss (`isOffline === true`), asserting successful native intent dispatch within $\le 5.5\text{ seconds}$.

---

## 4. Consequences

### Positive Consequences
- **Guaranteed Life-Safety Availability:** Emergency assistance functions reliably under cellular jamming, rural blackout, or server downtime.
- **Sub-Second Triggering:** Eliminates network latency; countdown initiates within $< 50\text{ ms}$ of trigger recognition.
- **Full TalkBack & Non-Visual Integration:** High-priority live region announcements and earcons provide clear feedback during the countdown.

### Negative Consequences / Trade-offs
- **Device-Specific Implementation:** Requires custom Android Kotlin native module implementation and device-specific hardware intent wiring.
- **Delayed Telemetry:** Server audit log cannot reflect emergency activations in real time if the device is offline; relies on asynchronous post-connection reconciliation.
