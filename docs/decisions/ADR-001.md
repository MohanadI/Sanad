# ADR-001: Separation of Generative AI Intent Classification from Deterministic Policy Enforcement and Tool Execution

**Status:** Accepted  
**Date:** 2026-09-12  
**Decision Maker:** Solution Architect / Technical Lead  
**Consulted:** Backend/AI Engineer, Security Lead, Product Lead  

---

## 1. Context & Problem Statement

Sanad is an assistive accessibility platform designed for blind and visually impaired Palestinian users. Unlike sighted users, blind users cannot visually inspect on-screen cards, modal confirmation dialogs, or system states to catch erroneous or hallucinated AI actions. 

Modern Large Language Models (LLMs) and conversational agents frequently exhibit:
1. **Non-deterministic behavior:** Identical prompts can produce different outputs or unexpected parameters.
2. **Susceptibility to Prompt Injection:** Malicious inputs (spoken or embedded in text/messages) can override system instructions.
3. **Hallucinations:** Ingesting colloquial dialects can lead models to fabricate recipients or misroute commands.

If an AI agent is given direct access to execution tools (such as placing cellular calls, sending messages, sharing location, or modifying calendars), a single hallucination or injection can result in severe financial, social, or physical harm.

---

## 2. Considered Alternatives

### Alternative A: Autonomous AI Agent (Function Calling / ReAct Pattern)
- Give the LLM access to tool definitions and allow the model to autonomously decide when and how to call tools.
- *Rejection Rationale:* Completely unacceptable from a life-safety and security standpoint. The model could execute sensitive actions without deterministic human-in-the-loop authorization, and security cannot be mathematically guaranteed.

### Alternative B: Direct UI Confirmation Cards
- The LLM triggers a native UI modal with text details for the user to review.
- *Rejection Rationale:* Sighted-centric design. Inaccessible to blind users who interact via audio and screen readers; does not protect against background execution flaws.

### Alternative C: Decoupled Pipeline with Deterministic Security Kernel (Selected)
- Enforce an absolute architectural separation:
  $$\text{User} \longrightarrow \text{AI/Intent} \longrightarrow \text{Structured Action} \longrightarrow \text{Policy Engine} \longrightarrow \text{Tool Executor}$$
- The AI is treated strictly as an untrusted interpreter producing a typed JSON DTO.
- A deterministic, rule-based Policy Engine evaluates permissions, risk tiers, and confirmation requirements.
- Stateless, bounded Tool Executors execute only when presented with a valid cryptographic authorization token.

---

## 3. Decision Outcome

We choose **Alternative C**.

### Architectural Invariants:
1. **AI NEVER Executes Tools:** No AI model or prompt agent shall have network access or code references to Tool Executors.
2. **Strict Schema Gate:** The output of the AI layer must validate against rigid Zod/JSON Schema contracts. Any unexpected key or malformed data triggers immediate rejection.
3. **Deterministic Policy Engine:** The Policy Engine contains zero machine learning, zero probabilistic models, and zero external I/O. Its decision logic is 100% deterministic and unit-testable.
4. **Single-Use Cryptographic Tokens:** High-risk actions require user confirmation, producing an HMAC-SHA256 time-bound authorization grant consumed on execution.

---

## 4. Consequences

### Positive Consequences
- **Mathematically Verifiable Security:** Authorization decisions can be exhaustively unit-tested against deterministic test matrices.
- **Immunity to Direct Tool Injection:** Prompt injection cannot force tool execution because the Policy Engine ignores natural language and evaluates only hardcoded capability rules.
- **Full Auditability:** Every step (intent proposed, policy decision, confirmation token, tool execution) generates an immutable, non-repudiable audit record.
- **Screen-Reader Optimization:** Confirmation challenges generate audio-first, concise spoken prompts tailored for blind users.

### Negative Consequences / Trade-offs
- **Increased Pipeline Latency:** Adding schema validation, policy evaluation, and token exchange adds an estimated $15\text{–}30\text{ ms}$ overhead to the request path (well within the acceptable latency budget).
- **Maintenance Overhead:** Every new capability requires authoring a formal intent schema, policy rule, risk classification, and bounded executor interface.
