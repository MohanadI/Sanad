# ADR-002: Modular Monolith Architecture (Node.js + TypeScript) and Free/Open-Source Stack for Initial Pilot

**Status:** Accepted  
**Date:** 2026-09-12  
**Decision Maker:** Solution Architect / Technical Lead  
**Consulted:** Backend Engineer, Mobile Engineer, DevOps/Security Lead  

---

## 1. Context & Problem Statement

Sanad is starting as a targeted pilot for 10–30 blind Palestinian users, built by a lean core engineering team of approximately 4 full-time-equivalent roles (Solution Architect, Backend/AI Engineer, Mobile Engineer, QA/Accessibility Engineer).

The project operates under two strict engineering constraints:
1. **Cost & Sustainability:** Avoid paid cloud AI APIs, paid telephony platforms, and proprietary infrastructure tiers during the MVP. The platform must be self-hostable on a donated server or low-cost Linux VPS.
2. **Operational Simplicity:** Avoid premature distributed systems complexity. Microservices, service meshes, and Kubernetes introduce immense operational drag, distributed tracing overhead, network failure modes, and serialization latency that a 4-person team cannot afford.

---

## 2. Considered Alternatives

### Alternative A: Microservices Architecture (Kubernetes / Multi-Repo)
- Separate containerized services for `auth-service`, `intent-service`, `policy-service`, `tools-service`, and `audit-service` communicating via gRPC or message brokers.
- *Rejection Rationale:* Massive overkill for 10–30 concurrent users. Introduces network hops that increase voice turnaround latency, distributed failure states, complex CI/CD, and requires dedicated DevOps personnel.

### Alternative B: Serverless Cloud Architecture (AWS Lambda / Cloud Run / Supabase)
- Event-driven functions deployed on public cloud provider free tiers.
- *Rejection Rationale:* Risk of vendor lock-in, sudden billing spikes if free quotas are exceeded, cold-start latency detrimental to real-time voice interactions, and geopolitical/data sovereignty concerns regarding cloud data centers in foreign jurisdictions.

### Alternative C: Modular Monolith in Node.js + TypeScript (Selected)
- A single unified backend codebase structured into strictly decoupled, isolated packages (`common`, `intent-classifier`, `policy-engine`, `tool-executors`, `audit-log`, `api-gateway`).
- In-process typed function calls across boundaries with zero serialization overhead.
- Deployed as a single container via Docker Compose on a Linux host, backed by PostgreSQL 16.

---

## 3. Decision Outcome

We choose **Alternative C: Modular Monolith**.

### Architectural Standards:
1. **Language & Runtime:** TypeScript 5.x on Node.js 20 LTS.
2. **Framework:** Fastify for high-performance, low-overhead HTTP/WebSocket routing.
3. **Database:** PostgreSQL 16 (relational integrity, JSONB support, row-level security, open-source).
4. **Boundary Isolation:** Enforced via TypeScript project references and `eslint-plugin-boundaries`. In-process communication adheres to the security pipeline without physical network hops.
5. **Future-Proof Extraction Path:** Because modules communicate through explicit DTO interfaces, any module (such as the Intent Classifier) can be extracted into an independent microservice in the future if horizontal compute scaling becomes necessary.

---

## 4. Consequences

### Positive Consequences
- **Low Operational Drag:** Single git repository, single build process, single CI/CD pipeline, and single Docker container to deploy and monitor.
- **Minimal Voice Latency:** Cross-boundary calls between Intent Classifier, Policy Engine, and Tool Executors are in-memory function calls ($< 1\text{ ms}$), preserving the strict $\le 1200\text{ ms}$ voice turnaround budget.
- **Zero Cloud Infrastructure Cost:** Runs efficiently on a single $10/month Linux VPS or an institutional/university donated server.
- **Atomic Database Transactions:** Cross-domain operations (e.g., alias update + audit log) can share transactional guarantees where necessary.

### Negative Consequences / Trade-offs
- **Coupling Risk:** Without strict governance, engineers could bypass package boundaries. *(Mitigation: Automated dependency-cruiser and ESLint rules in CI)*.
- **Single Point of Failure (SPOF):** A fatal unhandled crash halts the backend process. *(Mitigation: PM2/Docker auto-restart policies, health check endpoints, and isolated try/catch error boundaries)*.
